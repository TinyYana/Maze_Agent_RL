## 1. 專案理念:為什麼做這個

### 1.1 問題:遊戲難度是死的,玩家是活的

傳統遊戲的關卡難度是設計師手工調好的固定值。但玩家程度差異極大:
高手覺得無聊、新手覺得挫折。業界的解法叫 **動態難度調整 (DDA, Dynamic
Difficulty Adjustment)**,常見做法是寫死的規則(例如「玩家連死三次就降低怪物血量」)。

規則式 DDA 的問題:規則是人想的,涵蓋不了所有情境,而且容易被玩家察覺並利用。

### 1.2 本專案的答案:讓 AI 學會「當關主」

本專案不訓練 AI 玩遊戲,而是訓練 AI **出題**。我們建立一個名為
**Maze Master** 的強化學習代理人,它扮演「地下城主 (Dungeon Master)」的角色:

- 它即時觀察玩家在迷宮中的位置與整張地圖。
- 它每回合可以修改迷宮:放牆壁、拆牆、移動出口、放怪物。
- 它的目標**不是殺死玩家,也不是放水**,而是把玩家的通關時間精準控制在一個
  「不會太快、也不會太慢」的區間 — 也就是心流區間。

一句話總結理念:

> **把「遊戲關卡設計」這件事,從人工規則變成一個可以被機器學習最佳化的控制問題。**

### 1.3 這在學術上屬於什麼領域

本專案是 **PCGRL (Procedural Content Generation via Reinforcement Learning,
基於強化學習的程序化內容生成)** 的實作。PCGRL 由 Khalifa et al. (2020) 提出,
核心想法是把「生成遊戲內容」建模成 RL 問題:狀態是關卡現狀、動作是編輯操作、
獎勵是關卡品質指標。本專案的特色是把 PCGRL 從「離線生成關卡」推進到
**「線上即時編輯」**:Maze Master 在玩家遊玩的同時動態改造迷宮。

## 2. 核心概念:三個理論支柱

### 2.1 心流理論 (Flow Theory)

心理學家 Csikszentmihalyi 提出:當「挑戰難度」與「個人能力」匹配時,
人會進入高度專注且愉悅的「心流」狀態;挑戰太低會無聊,太高會焦慮。

本專案把心流**量化**成一個可計算的指標:**通關步數落在
`TIME_MIN`(50 步)~ `TIME_MAX`(100 步)之間即視為心流成功**。
這個量化讓「玩家體驗好不好」變成 RL 可以直接最佳化的數字。

### 2.2 PCGRL:內容生成即馬可夫決策過程

把迷宮編輯建模成標準的 MDP(馬可夫決策過程):

| MDP 元素 | 本專案的對應 |
|---|---|
| 狀態 (State) | 整張迷宮的影像表示(牆、玩家、出口、怪物的位置) |
| 動作 (Action) | 在座標 (x, y) 執行一種編輯:跳過 / 放牆 / 移除 / 移出口 / 放怪 |
| 獎勵 (Reward) | 玩家通關時間是否落在心流區間 + 各種編輯行為的即時回饋 |
| 轉移 (Transition) | 編輯生效 → 玩家走一步 → 怪物追一步 → 判定勝負 |

### 2.3 對抗但不敵對 (Adversarial but not Hostile)

Maze Master 與玩家是一種特殊的博弈關係:它要「刁難」玩家(太快通關會被扣分),
但**絕對不能把路堵死**(堵死是最重的懲罰之一,且環境會直接撤銷該操作)。
這個「必須保證關卡有解」的硬約束,是本專案與一般對抗式 RL 最大的差異,
也是遊戲 AI 設計中 **playability guarantee(可玩性保證)** 的實作。

├── models/                 # 模型備份與歷史實驗模型 (見 models/README.md)

設計原則:**環境邏輯、演算法、渲染、參數完全分離**。
改獎勵只動 `config.py`,改畫面只動 `rendering.py`,互不干擾。

### 3.2 一個回合 (env.step) 的完整流程

每次 `env.step(action)` 依序執行五個階段(見 `envs/maze_env.py:66`):

```
① Maze Master 編輯地圖   ← RL Agent 的動作在這裡生效
② 玩家移動               ← A* Bot 走一步(或讀取人類鍵盤輸入)
③ 怪物移動               ← 每隻怪物用 A* 朝玩家追一步
④ 碰撞處理               ← 玩家撞怪扣血,怪物消失
⑤ 狀態判定               ← 勝利 / 死亡 / 超時 / 太快 / 心流 / 太慢
→ 加總四類獎勵,回傳 (觀測, 獎勵, 是否結束, info)
```

這個「編輯者與玩家輪流行動」的回合制設計,讓單一個 Gymnasium 環境同時容納了
兩個行動者(Maze Master 與玩家),而 RL 訓練只針對 Maze Master。

## 4. 環境設計 (MazeEnv)

### 4.1 觀測空間 (Observation Space):AI 的眼睛

```python
spaces.Box(low=0, high=255, shape=(1, 60, 60), dtype=np.uint8)
```

- 迷宮是 15×15 的格子,每格是一個 ID(0 空地 / 1 牆 / 2 玩家 / 3 出口 / 4 怪物)。
- **地形與實體分離**:內部狀態中,`maze` 矩陣只儲存靜態地形(空地/牆),
  玩家、出口、怪物以座標清單追蹤,產生觀測時才疊合(優先序:玩家 > 出口 > 怪物)。
  這個設計是後期重構加入的 — 早期版本把所有東西寫進同一張格子,
  導致「怪物走過出口再離開時,出口被擦成空地」這類實體消失 bug。
  單一格子只能存一個 ID 的資料結構,天生無法表達「兩個東西在同一格」。
- ID 乘以 50 變成灰階亮度(0, 50, 100, 150, 200),再放大 4 倍成 60×60 單通道影像。
- **為什麼用影像而不是直接餵格子矩陣?** 因為搭配 CNN 策略網路,
  卷積核可以學到「空間局部特徵」(例如玩家附近的通道形狀),
  這對「要在哪裡放牆」這種空間決策至關重要。放大 4 倍是為了讓卷積核
  在小地圖上仍有足夠的感受野解析度。

### 4.2 動作空間 (Action Space):AI 的手

```python
spaces.MultiDiscrete([15, 15, 5] × ACTIONS_PER_TURN)
```

每個子動作由三個離散值組成:座標 x(0~14)、座標 y(0~14)、動作類型(0~4):

| 類型 | 名稱 | 效果 | 即時獎勵 |
|---|---|---|---|
| 0 | Skip | 什麼都不做 | -0.1(鼓勵行動) |
| 1 | Place Wall | 在空地放牆 | +3.0 基礎;路徑每變長一步 +0.5(上限 +15);牆蓋在玩家原路徑上再 +2.0 |
| 2 | Remove | 移除牆或怪物 | 0 |
| 3 | Move Exit | 把出口搬到 (x, y) | -0.3(避免濫用) |
| 4 | Spawn Monster | 放一隻 A* 追蹤怪(上限 3 隻) | 0 |

### 4.3 安全防護機制 (Guardrails)

環境內建三層保護,確保 Agent 再怎麼亂動也不會破壞遊戲:

1. **不可覆蓋玩家與出口**:動作座標落在玩家或出口位置 → 視為 Skip。
2. **不可堵死(核心)**:放牆或移出口後,立即用 A* 驗證「玩家到出口還有路」。
   若無路 → **撤銷該操作** 並給予 -5.0 懲罰。這就是可玩性保證的實作。
3. **動作白名單 (`set_allowed_actions`)**:可以限制 Agent 只能用某些動作,
   這是消融實驗(第 8 節)的基礎設施。

### 4.4 初始迷宮生成:DFS 完美迷宮

`envs/maze_generator.py` 使用**深度優先搜尋 (DFS) 挖洞法**:

1. 全地圖填滿牆壁。
2. 從 (0,0) 開始,每次隨機挑一個距離 2 格的未訪問鄰居,打通中間的牆。
3. 走到死路就回溯 (backtrack),直到所有格子都被訪問。

產出的是「完美迷宮」— 任兩點之間恰好一條路徑、無迴圈、保證連通。
出口固定在右下角 (14,14),玩家固定從左上角 (0,0) 出發。
之後的「多樣性」全部由 Maze Master 的動態編輯提供。

## 5. 獎勵函數設計 (Reward Engineering)

這是本專案最核心的工程,決定了 Agent 學到什麼行為。獎勵分成兩層:

### 5.1 終局獎勵 (Terminal Reward):定義「什麼叫做好」

| 結局 | 條件 | 獎勵 | 設計意圖 |
|---|---|---|---|
| ✅ Flow Success | 50 ≤ 通關步數 ≤ 100 | **+50** | 唯一的「大獎」,定義最終目標 |
| ⚠️ Too Fast | 步數 < 50 就通關 | **-25** | 重罰:太簡單=沒挑戰性 |
| ⚠️ Too Slow | 步數 > 100 才通關 | -15 | 太難或太繞=挫折感 |
| ⏰ Timeout | 超過 150 步還沒通關 | -15 | 遊戲拖沓 |
| ❌ Died | 玩家 HP 歸零 | -8 | 不希望玩死玩家,但懲罰比 Too Fast 輕 |
| 🚫 Blocked | 路徑被堵死 | -5(且操作被撤銷) | 硬約束的軟性補強 |

注意 **Too Fast (-25) 罰得比 Died (-8) 還重** — 這是刻意的:
寧可 Agent 激進到偶爾玩死玩家,也不要它消極不作為讓玩家秒過關。

### 5.2 過程獎勵 (Shaping Reward):引導學習方向

只靠終局獎勵,Agent 要在稀疏回饋中摸索太久(信用分配問題)。
因此加入即時的塑形獎勵:

- **放牆 +3.0**:直接鼓勵最有效的干預手段。
- **路徑延長獎勵 +0.5/步(上限 15)**:放牆後用 A* 重算最短路徑,
  路徑變長代表「有效刁難」,按延長量給獎勵。上限是為了防止 Agent
  刷出病態的超長迷宮。
- **牆蓋在原路徑上 +2.0**:精準攔截玩家的預定路線,比亂放牆更有價值。
- **Skip -0.1**:消極不作為要付出微小代價。
- **存活獎勵 +0.1/步(30 步後)**:遊戲進行得越久(在合理範圍內)越好。
- **撞怪 +1.0**:怪物成功干擾到玩家是有價值的資訊。

### 5.3 獎勵設計的迭代教訓

從 `config.py` 的註解可以看到調參軌跡:「放牆獎勵大幅提高」「太快懲罰加重」—
早期版本的 Agent 學到的最優策略是**什麼都不做**(因為亂動會被扣分,
不動至少不虧)。解法是雙管齊下:給 Skip 負獎勵 + 大幅提高放牆的即時獎勵,
把 Agent 從「消極均衡」推向「積極干預」。這是獎勵工程中典型的
**懶惰代理人 (lazy agent) 問題**與其解法,值得在報告中作為亮點呈現。

## 6. 訓練方法 (PPO)

### 6.1 為什麼選 PPO

PPO (Proximal Policy Optimization, Schulman et al. 2017) 是目前
policy-gradient 家族中最穩定、最通用的演算法:

- **支援 MultiDiscrete 動作空間**(DQN 不支援;本專案動作是 15×15×5 的組合)。
- **Clipped objective** 限制每次策略更新的幅度,避免一次壞更新毀掉整個策略 —
  對獎勵函數還在迭代的專案特別重要。
- Stable-Baselines3 的 PPO 實作成熟,支援 CNN 策略、TensorBoard、Callback。

### 6.2 超參數設定(`train.py:101`)

| 參數 | 值 | 說明 |
|---|---|---|
| Policy | `CnnPolicy` | NatureCNN 架構,吃 60×60 灰階影像 |
| learning_rate | 3e-4 | SB3 預設,穩定起點 |
| n_steps | 4096 | 每次更新收集的 rollout 長度(回合較長,需要大 buffer) |
| batch_size | 256 | |
| gamma | 0.99 | 折扣因子:重視長期(終局)獎勵 |
| gae_lambda | 0.95 | GAE 優勢估計,平衡偏差與變異 |
| clip_range | 0.2 | PPO 標準裁剪範圍 |
| **ent_coef** | **0.1** | **熵係數刻意調高**(SB3 預設 0.0):強迫 Agent 持續探索,是解決「懶惰代理人」的第二道保險 |
| total_timesteps | 500,000(可用環境變數 `TRAIN_TIMESTEPS` 覆寫) | |
| n_envs | 8 (SubprocVecEnv) | 多進程並行收集;n_steps 除以環境數,維持每次更新總量 4096 |

### 6.2.1 硬體與效能注意事項

- **Windows GPU 陷阱**:PyPI 預設安裝 CPU 版 PyTorch(`2.9.1+cpu`),
  訓練會默默跑在 CPU 上。需改用 `--index-url https://download.pytorch.org/whl/cu128`
  安裝 CUDA 版。`train.py` 啟動時會印出運算裝置並在缺少 CUDA 時警告。
- **真正的瓶頸在環境,不在網路**:環境步進含多次純 Python A* 尋路,是 CPU 密集操作。
  單環境約 260 fps;改用 8 進程 SubprocVecEnv 後約 950+ fps(RTX 4070 實測),
  50 萬步訓練從約 30 分鐘縮短到約 9 分鐘。
- 每個子進程環境使用不同亂數種子,避免所有進程產生相同的迷宮序列。

### 6.3 訓練流程

```
train.py
 ├─ 產生 run_id(時間戳記)→ 每次實驗的 log / 模型 / 除錯圖各自歸檔
 ├─ PPO 與 MazeEnv 互動收集經驗 → GAE 估計優勢 → clipped 更新
 ├─ SaveObservationCallback:每 1000 步把「AI 眼中的迷宮」存成彩色 PNG
 ├─ TensorBoard 記錄 reward / loss / entropy 曲線
 └─ 存檔:maze_master_ppo.zip(主模型)+ models/ 底下的歷史備份
```

## 7. 模擬玩家:A* 導航機器人

訓練 RL 需要海量回合(50 萬步),不可能用真人玩家,因此用
**A\* 尋路機器人模擬玩家**(`agents/astar_bot.py`):

- 標準 A*:g(已走步數)+ h(曼哈頓距離啟發式),4-方向移動,最短路徑保證。
- **可調隨機性 (`AI_RANDOMNESS`)**:在啟發式 h 上疊加 ±randomness 比例的雜訊,
  讓 Bot「誤判」某些遠路比較近。0.0 = 完美玩家,1.0 = 路痴新手。
  這個參數等於**玩家能力模型**,是模擬不同程度玩家的機制。
- 同一套 A* 也被怪物拿來追玩家、被環境拿來驗證「路徑沒被堵死」— 一魚三吃。

### 7.1 玩家個性隨機化 (Player Profile Randomization)

只對「完美 A*」訓練的模型,泛化能力堪憂 — 真實玩家會繞路、會停下來想。
因此訓練時 (`config.PLAYER_PROFILE_RANDOMIZE = True`) **每回合隨機抽樣玩家個性**:

| 參數 | 抽樣範圍 | 模擬的行為 |
|---|---|---|
| `player_randomness` | 0.0 ~ 0.8 | 繞路程度(A* 啟發式雜訊) |
| `player_hesitate_prob` | 0.0 ~ 0.3 | 猶豫機率:該回合玩家不動,但 Maze Master 仍可編輯 |

這相當於一種 **domain randomization**:模型在訓練中面對整個「玩家能力光譜」,
而不是單一對手。演示 (`main.py`) 與評估 (`evaluate.py`) 預設關閉此機制,
使用固定個性以確保可重現性。

人類模式 (`PLAYER_MODE = "HUMAN"`) 則改讀鍵盤方向鍵,並提供 2 次「破牆鎚」
(hammer) 對抗 Maze Master 的刁難,可親身體驗被 AI 出題的感覺。

## 8. 實驗設計與結果

### 8.1 消融實驗 (Ablation Study)

`experiment_runner.py` 利用動作白名單機制,固定同一個模型、只改變允許的動作,
比較四種場景各 100 回合:

| 場景 | 允許動作 | 意義 |
|---|---|---|
| 1. Static Maze | 只能 Skip | **基準線**:純 DFS 迷宮,無 AI 干預 |
| 2. Walls Only | Skip + 放牆/拆除 | 只靠地形改造 |
| 3. Walls + Monsters | 再加怪物 | 地形 + 威脅 |
| 4. Full Features | 全部(含移出口) | 完整能力 |

### 8.2 代表性結果(2026-01-06 實驗批次)

| 場景 | 平均步數 | 成功率 | 心流率 | 平均剩餘 HP |
|---|---|---|---|---|
| 1. Static Maze | 59.3 | 100% | 73% | 3.00 |
| 2. Walls Only | 55.7 | 100% | 53% | 3.00 |
| 3. Walls + Monsters | 53.4 | 90% | 50% | 2.58 |
| 4. Full Features | 53.6 | 93% | 48% | 2.76 |

### 8.3 結果解讀(誠實版)

- **可玩性保證有效**:所有場景成功率 ≥ 87%,Agent 干預下遊戲仍幾乎必定可通關。
- **怪物確實造成威脅**:場景 3/4 的平均 HP 下降(3.0 → ~2.6),
  證明 Agent 學會用怪物施壓而非擺飾。
- **目前的誠實限制**:在此組 TIME_MIN/TIME_MAX 設定下,靜態迷宮的心流率(73%)
  反而高於 Agent 干預(48~53%)。原因是 15×15 DFS 迷宮的天然通關步數
  剛好多落在 50~100 區間,基準線本身偏高;而 Agent 的干預帶有攻擊性,
  會把部分回合推出區間。這指向兩個後續方向:(a) 調整心流區間定義或
  以「步數變異數收斂」為指標,(b) 針對 `AI_RANDOMNESS > 0` 的非完美玩家測試 —
  對付會迷路的玩家時,動態調整的價值才會真正顯現(靜態迷宮無法對玩家程度做出反應)。
  報告或簡報中建議直接面對這個數據,把它講成「發現與洞察」而不是隱藏它。

### 8.4 評估工具

- `evaluate.py`:單一模型 1000 回合,輸出心流率、存活率、結果分佈、
  平均步數/HP/獎勵的文字報告(存於 `evaluation_logs/`)。
- `experiment_runner.py`:上述消融實驗,輸出原始 CSV + 摘要 CSV
  (存於 `experiment_log/`),可直接用 pandas / Excel 畫圖。
- `adaptation_check.py`:動態調整能力檢驗(見 8.5)。
- 評估時 `deterministic=True`(可重現);演示 `main.py` 用
  `deterministic=False`(保留隨機性,畫面較生動)。

### 8.5 動態調整能力檢驗 (Adaptation Study)

「AI 會不會隨玩家表現動態調整」是本專案的核心宣稱,`adaptation_check.py`
從兩個層次檢驗它(每組 100 回合、各組共用同一批迷宮種子以控制變因):

1. **跨玩家個性**:讓同一個模型分別對戰「高手(完美 A*)/普通(繞路 0.4)/
   手殘(繞路 0.8 + 猶豫 0.3)」,比較行為分布與結果。
2. **回合內節奏**:每步用 A* 估計玩家的預計抵達步數,分成「預估太快/剛好/太慢」
   三種狀態,統計模型在各狀態下的動作選擇。

#### 對照結果:舊模型(只對完美 A* 訓練)vs 新模型(玩家個性隨機化訓練)

| 指標 | 舊模型 | 新模型 |
|---|---|---|
| 心流率(高手/普通/手殘) | 48% / 50% / 47% | 51% / 51% / 47% |
| Too Fast 比例(平均) | ~51% | **~39%(明顯下降)** |
| 干預率:玩家預估太快時 | 分布幾乎不隨節奏變化 | 39%(多數時候按兵不動) |
| 干預率:玩家預估太慢時 | 同上 | **81%(積極出手)** |
| 玩家落後時的拆牆(開路)比例 | 無明顯變化 | 45.5%(平時 ~24%) |
| 玩家死亡率 | ~0% | ~10%(怪物使用增加的代價) |

#### 解讀(誠實版)

- **舊模型**基本上是一套「平均有效的固定干預風格」:對誰都差不多,
  動作分布不隨玩家節奏變化 — 動態調整能力很弱。
- **新模型**出現了明確的狀態相依行為:玩家進度落後時干預率從 39% 跳到 81%,
  且拆牆(幫玩家開路)比例顯著上升;整體 Too Fast 比例下降 12 個百分點。
  這是「幫慢玩家、擋快玩家」的正確方向。
- **代價與注意事項**:(a) 新模型更常放怪,玩家死亡率升到約 10% —
  這與 `REWARD_HIT` 正獎勵有關,可視需求調整;(b)「預估太慢」狀態
  只佔全部樣本約 2%,該列統計參考性有限;(c) 此檢驗是**觀察性相關而非因果**
  (AI 蓋牆多的回合玩家自然變慢),嚴格的因果檢驗需要介入式實驗。
- 心流率仍卡在 ~50%:主要瓶頸推測是觀測缺乏時間資訊(見 §11 第 4 點),
  模型無法精確知道「現在該收手還是該加壓」。

## 9. 工程實務:除錯、打包、CI

### 9.1 AI 視野可視化 (`SaveObservationCallback`)

RL 最難除錯的問題是「AI 到底看到了什麼」。本專案在訓練中每 1000 步
把觀測矩陣轉成彩色 PNG(空地米白、牆深灰、玩家藍、出口金、怪物紅)存進
`debug_vision/run_時間戳/`。曾靠這個工具發現觀測值視覺對比不足的問題。
這是「用工程手段解決 ML 黑箱問題」的好例子。

### 9.1.1 環境不變式煙霧測試 (`test_smoke.py`)

地形/實體分離重構後,加入可重跑的最小回歸測試:隨機動作跑 2000 步,
逐步驗證「地形層只含空地與牆」「出口與玩家永不消失」「怪物不卡牆」
「觀測形狀與 dtype 不變(確保與已訓練模型相容)」。`python test_smoke.py` 即可執行。

### 9.1.2 演示層 (Demo Layer)

針對「評審與外賓只看得懂畫面」的現實,`rendering.py` 實作了完整的演示層:

- **頂部 AI 狀態列**:即時顯示 Maze Master 每步決策的自然語言描述
  (「蓋牆 (3, 5)」「想堵死路徑 → 被規則撤銷」),把黑箱決策可視化。
- **心流節奏條**:底部儀表板將 reward 設計直接視覺化 — 綠色區段是
  AI 的 50~100 步目標區間,白色游標是玩家目前進度。
- **遊戲內教學**:`?` 按鈕 / H 鍵開啟中文說明面板,內容涵蓋 RL 目標說明。
- **視覺回饋**:AI 每種編輯動作有對應顏色的擴散光圈、受擊紅閃、
  回合結束橫幅、玩家移動平滑插值與殘影、出口脈動光暈。
- 深色主題;中文字型依平台直接指定字型檔路徑載入(Windows 微軟正黑體 /
  macOS Hiragino Sans GB / Linux Noto Sans CJK),避免預設字體缺字變成豆腐框。
  不用 `pygame.font.SysFont` 是因為它在 Windows 會掃描字型登錄檔,
  遇到非字串的登錄值會拋 TypeError,打包成 exe 後一開就閃退。
- 畫面固定 60 FPS 更新,事件輪詢與 AI 推進速度(`AI_STEP_FPS`)脫鉤,
  確保 HUMAN 模式按下方向鍵能立即得到反饋。

### 9.2 實驗管理

每次訓練以時間戳記為 run id,TensorBoard log、除錯圖、模型備份
三者都按 run 歸檔 — 簡易但完整的實驗追蹤 (experiment tracking)。

### 9.3 發佈:PyInstaller + GitHub Actions

- `MazeGame.spec` 定義打包:把 `main.py`、模型 zip、SB3 資料檔
  打成單一 Windows 執行檔 `MazeGame.exe`。
- `main.py` 的 `resource_path()` 處理 PyInstaller 的 `_MEIPASS` 暫存路徑,
  讓模型檔在打包前後都能正確載入。
- `.github/workflows/build-maze-game.yml`:push 後自動在雲端 Windows
  跑打包,產出可下載的執行檔 — 評審或外賓不需要裝 Python 就能玩。

## 11. 已知限制與未來方向

1. ~~**玩家模型單一**~~ **(已處理)**:訓練已改為每回合隨機抽樣玩家個性
   (§7.1),並有 `adaptation_check.py` 系統性驗證對不同水準玩家的行為(§8.5)。
   後續可再引入真人遊玩資料校準玩家模型。
2. **心流指標簡化**:只用步數區間,未考慮 HP 消耗、緊張節奏等維度。
   → 多目標獎勵或以步數變異數收斂為指標。
3. **靜態基準線偏高**:見 8.3;心流區間的選定與迷宮尺寸耦合。
4. **觀測無時間資訊**:單幀影像看不出玩家已走多少步,Agent 缺乏
   「該收手了」的訊號。這是 §8.5 中「對玩家節奏的細緻調整偏弱」的
   最可能結構性原因。→ 觀測加入步數通道或改用 frame stacking。
5. **固定起訖點**:玩家永遠左上、出口永遠右下開局,可能造成策略過擬合。
